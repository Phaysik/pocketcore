# Pokemon Construction API

**Status:** Option C API implemented.

**Decision:** Option C, a `PokemonSpec` builder struct with `std::optional` fields
and a single `instantiate(spec)` entry point.

## Problem and goals

The construction API must distinguish between caller-supplied instance data and
data generated by the engine. Adding one nullable pointer per property makes
call sites difficult to read and leaves omission semantics implicit.

The design must:

- Make explicit versus generated construction obvious at the call site.
- Support generated construction with selected caller-supplied overrides.
- Define which values come from callers, generation policies, and metadata.
- Permit deterministic generation through supplied random sources.
- Guarantee that explicit construction never generates a field.
- Keep every public constructor below or equal to five nullable parameters.
- Keep runtime instantiation in the registry layer rather than the metadata
  configuration facade.

This document evaluates the three ticket options and defines the selected
design's construction contract. The implementation status and remaining
verification work are recorded below.

## Current implementation

The ticket describes the nullable-input API introduced in 0.12.26. The current
repository has already moved instantiation into
[PokemonRegistry](../include/Registry/pokemonRegistry.h), with its implementation
in [pokemonRegistry.cpp](../src/Registry/pokemonRegistry.cpp).
[PokemonRegistryConfiguration](../include/Configuration/pokemonRegistryConfiguration.h)
provides metadata configuration and read-only runtime registry access.

The current entry point accepts `const PokemonSpec&`, a registry dependency
bundle by const reference, and supplied `BattleRandomSources`. The spec composes
three existing contexts:

- `IDContext` borrows nature, ability, item, and move sequences.
- `IVEVContext` borrows IV and EV sequences.
- `PokemonBreedingContext` borrows optional breeding parents.

Empty input spans select automatic behavior. For missing natures, abilities,
items, moves, and IVs, encounter-provided values take precedence over the
generation helpers. Otherwise, moves are selected from the learnset and
encounter, and the remaining fields use their generation policies; missing EVs
become zero. Optional level and gender values are used when supplied. Otherwise,
level comes from encounter metadata (using supplied random sources for variable
levels), and gender is sampled from the species pool. The gender draw occurs
only in the omitted-value branch.

Supplying all six sequences plus level and gender now provides the
no-generation path. The implementation still looks up learnset metadata and
validates encounter metadata when an index is supplied. No in-repository calls to
the superseded instantiation signature were found during the implementation review.

The existing low-level [Pokemon constructors](../include/Pokemon/pokemon.h)
accept references and values, not a wall of nullable property pointers. They
materialize resolved instance data and need not become generation APIs.

## Terminology

- **Caller-supplied:** An instance value selected by the caller and validated
  without substitution by a generation policy.
- **Generated:** An instance value selected by the engine, either randomly or
  deterministically from an encounter or learnset policy.
- **Metadata-resolved:** Definition data looked up using selected identifiers,
  such as species base stats, move PP, and nature multipliers.
- **Derived:** State calculated from the completed instance inputs, such as
  calculated stats and initial full health.

Metadata resolution and stat calculation are not generation.

## Options

### Option A: Nullable parameters and PokemonBuildIntent

Retain nullable property parameters and add a `PokemonBuildIntent` enum with
`Explicit` and `Generated` values. Doxygen defines null-means-generate for each
property on generated calls. Explicit intent rejects missing required inputs
and must accept caller-supplied level and gender.

**Advantages**

- Closest to the historical API and potentially the smallest migration.
- Intent is visible when the enum is written at the call site.
- Preserves partial generation through individual null inputs.

**Disadvantages**

- The enum does not remove positional ambiguity or long parameter lists.
- Explicit intent plus null required properties remains representable and
  requires runtime rejection.
- Every new property expands the signature and its documentation.
- A direct nullable-per-property constructor with more than five nullable
  parameters violates the ticket constraint. Grouping properties avoids that
  limit but no longer solves the original readability problem by itself.

**Assessment:** Viable as a transition, but not recommended as the long-term
API. Factory functions must not be used as a loophole to retain the same
nullable-pointer wall.

### Option B: instantiateExplicit and instantiateGenerated

Expose two named registry functions. Use purpose-fit value aggregates rather
than another long positional signature:

- `ExplicitPokemonSpec` contains all selectable instance fields, with no
  optional generation fields.
- `GeneratedPokemonSpec` contains a required species ID and encounter index,
  optional value overrides, and breeding context.

Conceptual signatures, not declarations of existing APIs:

```cpp
std::expected<Pokemon, PokemonInstantiationError> instantiateExplicit(
    const ExplicitPokemonSpec &spec,
    const PokemonInstantiationDependencies &dependencies) const;

std::expected<Pokemon, PokemonInstantiationError> instantiateGenerated(
    const GeneratedPokemonSpec &spec,
    const PokemonInstantiationDependencies &dependencies,
    const BattleRandomSources &randomSources) const;
```

**Advantages**

- Function names make intent unambiguous.
- Explicit construction has no RNG parameter or generation fallback.
- Required explicit values and optional generated overrides have distinct
  representations.
- Adding a property extends an aggregate instead of adding positional pointers.
- Both paths can share metadata resolution and materialization.

**Disadvantages**

- Introduces two input types and two entry points.
- Callers choosing a mode dynamically must branch.
- Shared validation must be factored carefully to avoid behavioral drift.

**Assessment:** Provides the strongest distinction through function names, but
is not selected. Two input types and entry points are unnecessary when a single
spec can express supplied and generated fields independently.

### Option C: PokemonSpec and instantiate(spec)

Introduce one `PokemonSpec` aggregate that composes the existing contexts, uses
`std::optional` for optional scalar inputs, and provides a single registry
`instantiate(spec)` entry point. Present fields supply values.
Omitted fields request automatic behavior independently for each property.
There is no construction-wide intent enum or mutually exclusive mode.

**Advantages**

- Named fields eliminate positional nullable parameters.
- Supports partial generation naturally and scales to new properties.
- One input type is convenient for dynamically assembled requests.
- Reuses the existing context types and their per-field helper behavior.
- Non-empty context spans distinguish supplied slots from automatic selection.

**Disadvantages**

- A fully populated spec does not make explicit intent as visible as a named
  explicit function.
- Adding a new optional field can silently turn an old fully populated call
  into a partially generated call.
- Callers requiring no generation must supply every selectable instance field;
  there is no separate mode that rejects omissions.
- A universal spec can mix encounter-only and explicit-only concerns.

**Assessment:** Selected. Named contexts and optional scalar fields support mixed construction and
future properties without expanding a positional signature or introducing
separate spec types. It preserves the existing helpers' fine-grained combination
of supplied and automatically selected values rather than imposing an
explicit-versus-generated mode on the entire instance.

## Selected contract for Option C

### Input representation

`PokemonSpec` is a value aggregate built using named member initialization,
not a fluent builder framework. It contains:

- A required species ID.
- An `IDContext` member containing the existing nature, ability, item, and move
  spans.
- An `IVEVContext` member containing the existing IV and EV spans.
- A `PokemonBreedingContext` member containing the existing parent pointers.
- `std::optional` fields for level and gender.
- An optional `std::size_t` encounter index, defaulting to `std::nullopt`.

These context types are reused directly from
[pokemonInstantiationContext.h](../include/Pokemon/pokemonInstantiationContext.h),
not flattened into top-level arrays or replaced with optional array types.
An empty span requests automatic behavior for that field; a non-empty span
supplies values. Optional scalars use `std::nullopt` for omission.

Each present instance field is validated and used without generating that
field. Each absent instance field uses the policies in the provenance table
below. These decisions are independent: a single spec may supply moves and EVs
while generating natures, abilities, items, and IVs.

A fully explicit construction supplies every selectable instance field,
including level and gender, and generates nothing. Registered learnset metadata
is still required. An encounter index is optional when a level is supplied; if
present, it must identify an active encounter. Breeding parents are only used
by automatic egg ability selection when the encounter does not supply abilities.
Breeding parent pointers remain non-owning.

Implemented entry-point signature:

```cpp
std::expected<Pokemon, PokemonInstantiationError> instantiate(
    const PokemonSpec &pokemonSpec,
    const PokemonInstantiationDependencies &dependencyRegistries,
    const BattleRandomSources &randomSources) const;
```

Dependencies and random sources remain separate runtime services, not optional
instance properties. The single entry point uses random sources only for
omitted fields whose automatic policy requires randomness.

Per-field choices are visible in named initialization:

```cpp
PokemonSpec mixedSpec{
    .mIDContext = {.mMoveIDs = suppliedMoveIDs},
    .mIVEVContext = {.mEVs = suppliedEVs},
    .mEncounterIndex = encounterIndex,
    .mPokemonID = speciesID,
};
```

Here moves and EVs are caller-supplied; omitted fields use automatic policies.
The initializer follows the implemented struct's member declaration order.
When a new selectable field is added, its omission policy must be documented
and fully explicit call sites and tests updated to supply it.

Context spans borrow caller-owned storage. A non-empty span containing no-ID
sentinels means deliberately unused slots, not a request to generate
replacements. An empty span means automatic selection, not explicitly empty
slots. A supplied zero EV array and an empty EV span both produce zero EVs,
but communicate different caller intent.

### Field provenance

| Field                                            | Supplied scalar or non-empty context span               | Omitted scalar or empty context span                                                               |
| ------------------------------------------------ | ------------------------------------------------------- | -------------------------------------------------------------------------------------------------- |
| Species ID                                       | Caller-supplied                                         | Caller-supplied                                                                                    |
| Level                                            | Caller-supplied                                         | Fixed encounter level or sampled inclusive encounter range                                         |
| Gender                                           | Caller-supplied                                         | Sampled from the species gender pool                                                               |
| Nature IDs                                       | Caller-supplied                                         | Encounter values, otherwise selected using registered nature generation policy                     |
| Ability entries                                  | Caller-supplied                                         | Encounter values, otherwise selected from the species pool; egg inheritance uses breeding context  |
| Item IDs                                         | Caller-supplied, including empty slots                  | Encounter values, otherwise selected using the species item pool policy                            |
| Move IDs                                         | Caller-supplied, including empty slots                  | Encounter values, otherwise selected from learnset and encounter eligibility at the resolved level |
| IVs                                              | Caller-supplied                                         | Encounter values, otherwise sampled within valid IV bounds                                         |
| EVs                                              | Caller-supplied                                         | Initialized to six zero values; not randomly sampled                                               |
| Name, base stats, types, egg groups, learnset ID | Resolved from species metadata                          | Resolved from species metadata                                                                     |
| Move maximum/default PP                          | Resolved from selected move metadata                    | Resolved from selected move metadata                                                               |
| Nature multipliers                               | Resolved from selected nature metadata                  | Resolved from selected nature metadata                                                             |
| Calculated stats and level damage factor         | Derived from completed inputs                           | Derived from completed inputs                                                                      |
| Initial health, current PP, statuses             | Full calculated health, default move PP, empty statuses | Same initialization                                                                                |

A present value is validated and retained without sampling that field.
Supplied moves continue to require registered metadata, not encounter
eligibility; automatically selected moves use learnset eligibility.

### Validation and errors

The following requirements include remaining hardening work; they do not imply
that every check has already been implemented.

- Preserve `std::expected<Pokemon, PokemonInstantiationError>` and existing
  domain-specific validation errors. Add a specific error only where the
  existing error vocabulary cannot express a new failure.
- Require the dependency bundle by const reference. Validate member pointers
  before use. The current implementation requires learnset metadata even for
  fully supplied construction; removing that dependency is a possible follow-up,
  not part of the implemented API contract.
- Validate explicit values and present overrides before materialization.
  Invalid data must return an error, never trigger generation.
- Reuse the per-field supplied/automatic branches in
  [pokemonHelpers.cpp](../src/Pokemon/pokemonHelpers.cpp). Forward context spans
  directly, preserving non-empty sentinel-only spans and empty-span automatic
  behavior; do not add a construction-wide completeness gate.
- Enforce array capacities, IV/EV constraints, scalar ranges, and identifier
  registration before copying or dereferencing metadata.
- Preserve existing documented duplicate normalization where applicable, but
  never fill vacated slots with generated values.
- Reject encounter indexes at or beyond the array size, unused encounter slots,
  invalid level ranges, and empty gender pools before indexing or sampling.
- Report required missing breeding parents when generating egg abilities;
  supplied ability entries do not trigger inheritance.

### Randomness, ownership, and Doxygen

All random draws, including variable encounter levels, use supplied random
sources. Identical validated metadata, specs, parent inputs, and reset
deterministic source states must yield identical instances. This does not
promise identical sequences across future generation-policy changes.

A fully supplied spec must consume no randomness and invoke no automatic
selection. Mixed specs generate only omitted fields. Shared materialization
operates only on fully resolved values.

Specs contain contexts by value, but copying those contexts copies spans and
parent pointers, not the referenced data. Caller-owned span storage, dependencies,
and breeding parents must remain valid throughout instantiation; storing or
copying a spec does not extend their lifetime. Returned Pokemon values own their
instance arrays, but their display name
still borrows metadata storage as described in
[the ownership contract](./pokemon-ownership.md).

Doxygen on the single entry point and `PokemonSpec` must enumerate the provenance
above, per-field presence/absence and sentinel semantics, error behavior,
and lifetime requirements. It states that a fully supplied spec generates no
fields and consumes no randomness. For omitted fields, it identifies each
random selection, deterministic selection, zero default, and metadata-derived
value. No `PokemonBuildIntent` is introduced by the selected design; that enum
belongs only to the evaluated Option A.
